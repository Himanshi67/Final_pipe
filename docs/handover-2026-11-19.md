# Handover: Final_pipe catalog pipeline (state on 2026-11-19)

## 1. What the pipeline does

It changes a list of SKUs into a verified WooCommerce import for an appliance store.
No LLM is called in this code.

    SKU list (.xlsx)
      -> sku_enricher.py     finds each product online, writes <name>_filled.xlsx
      -> person reviews      approve or skip each row in the GUI
      -> app.py              builds the WooCommerce CSV + SKU_n.webp images
      -> validate_csv.py     quality gate, writes validation_issues.csv
      -> WooCommerce import  manual CSV import, or wc_publish.py (REST API)

The GUI (`gui.py`) runs all five steps: enrich, review, build, validate, publish.

## 2. How to run it

Python is always `.venv\Scripts\python.exe`. Do not use bare `python`.

1. Put the SKU list in `inputs\`. Example: `inputs\LIST.xlsx`.
2. Start the GUI: `.venv\Scripts\python.exe -m streamlit run gui.py`
3. Step 1: upload the list and start the crawl. The result goes to `runs\<name>\`.
4. Step 2: examine each row. Approve a good row. Skip a bad row (a reason is optional).
5. Step 3: build. The default builds the approved rows only.
6. Step 4: validate. Correct each blocking issue.
7. Step 5: publish. This step is a dry run unless you select the commit.

A test without the GUI, for 3 SKUs:

    .venv\Scripts\python.exe sku_enricher.py "inputs\LIST.xlsx" --limit 3

Rules that prevent damage:

- Do not give a `*_filled.xlsx` file to the enricher as input.
- Do not open the output file in Excel during a run.
- `wc_publish.py --commit` writes to the LIVE store. Read the publish guards in
  `CLAUDE.md` before you use it.
- Store credentials are in `clients\<slug>\.env`. That file is not in git. Do not put
  credentials in the repo or in a chat.

## 3. How the online search works

For each SKU, the steps occur in this order. A complete product stops the flow.

| Step | Source | Cost |
|---|---|---|
| 0a | Local sitemap index (`url_index\index.sqlite`) | Free |
| 0b | Retailer site search (Croma, Reliance Digital) | Free |
| 1 | serper.dev search | Paid: 1 credit for each query |
| 2 | DuckDuckGo, only when serper gives no answer | Free |
| 3 | Donor pages complete a missing price or photos | Free |

Pages and search results stay in `.cache\` for 14 days. A second run of the same list
uses the cache and costs nothing.

Settings in `clients\<slug>\client.toml`, table `[serper]`:

| Key | Values | Meaning |
|---|---|---|
| `query_mode` | `incremental` / `batch` | `incremental` sends one paid query, opens the pages, and stops at the first complete product. `batch` sends all queries of a tier first (the old behaviour, more credits). |
| `search_order` | `paid_first` / `free_first` | `free_first` tries DuckDuckGo before serper. It is slower and less reliable for a large batch. |
| `default_run_budget` | number | Maximum credits for one run. 0 = no limit. |

**Present value: `query_mode = "incremental"`.** The owner approved it on 2026-11-19.
If more rows become `NOT FOUND`, change it to `"batch"`.

If the run prints a warning that the sitemap index is empty, run:

    .venv\Scripts\python.exe url_index.py refresh
